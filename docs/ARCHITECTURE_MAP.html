Robot Safety Monitor · 구조 지도

설정 파일 한 장이 감시 파이프라인을 만든다

RSM은 로봇의 내부·외부 위험을 감지하는 모듈을 표준 트레이트로 규격화하고, YAML 선언만으로 조합하는 프레임워크다. 이 문서는 전체 구조와 rsm-core의 모듈들이 런타임에 어떻게 맞물리는지를 그림으로 정리한다. 코드를 읽는 순서는 CODE_TOUR.md가 안내한다.

범위 감지 · 판단 · 알림 (제어 명령 발행 제외) 언어 Rust edition 2024 현재 Phase 0 완료 (상세는 STATUS.md)

A네 단계와 두 개의 가로대

파이프라인은 Source → Detector → Arbiter → Sink 네 단계다. 그 아래를 가로지르는 두 가지가 프레임워크의 성격을 결정한다. 모든 모듈이 같은 주입된 시계를 보고, 모든 모듈을 Supervisor가 감시한다.

B흐르는 데이터는 세 가지뿐

단계 사이를 오가는 타입이 셋으로 고정돼 있어서, 모듈을 추가해도 배관은 그대로다. 이게 “코어 수정 0줄로 모듈 추가”가 성립하는 이유다.

타입만드는 쪽쓰는 쪽내용
SignalSourceDetector 관절 각도·토크, 거리, 온도, 전압 같은 원시 관측값. 고정 enum이라 새 variant를 늘리면 처리 안 한 곳이 전부 빌드 에러로 드러난다.
HazardEventDetectorArbiter “토크 한계를 넘었다”는 한 건의 관측. 심각도·확신도·근거·TTL을 담는다. TTL 동안만 유효한 주장이라 갱신이 끊기면 스스로 소멸한다.
SafetyStateArbiterSink 종합 심각도 + 활성 위험 목록 + 감시 가용성. 소비 시스템이 보는 최종 산출물.

심각도는 순서형이다

NONE ADVISORY WARNING CRITICAL

순서가 있으므로 Arbiter의 기본 정책이 한 줄이 된다. 활성 이벤트의 심각도 중 최댓값을 취하고, TTL이 지난 것은 목록에서 빠진다.

설계 귀결

fast 그룹은 1 kHz로 돌면서 tick 경로에서 힙 할당이 0이어야 한다. 그래서 HazardEvent에는 String이나 Vec을 넣을 수 없다. 모듈 이름과 위험 타입은 설정 로드 시점에 인터닝된 정수 ID로 바꾸고, 근거(evidence)는 고정 크기 배열로 담는다. 문자열로 되돌리는 것은 Sink에서 출력할 때뿐이다.

// 이렇게 쓰면 tick 마다 할당이 생긴다
struct HazardEvent { source: String, kind: String, evidence: Vec<(String, f64)> }   // ✗

// 설정 로드 때 한 번 인터닝하고, 런타임에는 정수만 다룬다
struct HazardEvent { source: ModuleId, kind: HazardTypeId, evidence: EvidenceSet }  // ✓

C런타임 — 스레드와 큐

주기 그룹 하나가 OS 스레드 하나다. 그룹 안에서는 모듈이 정해진 순서로 순차 실행되고, 그룹 사이는 wait-free SPSC 링버퍼로만 이어진다. 느린 모듈이 빠른 모듈을 막지 못하게 하는 구조다.

E기동할 때 무슨 일이 일어나나

여기가 “설정만으로 조합”이 실제로 벌어지는 지점이다. 모든 동적 결정과 메모리 할당이 이 구간에서 끝나고, 그 뒤로는 고정된 구조가 반복해서 돌 뿐이다.

  1. YAML 파싱 — serde로 주기 그룹, 모듈 목록, 파라미터, 신호 연결을 읽는다. 모르는 필드가 있으면 여기서 실패한다. 오타가 조용히 무시되는 것을 막기 위해서다.
  2. 레지스트리 조회 — 설정이 참조한 이름이 등록되어 있는지 확인한다. 없으면 UnknownModule로 기동 실패. 실행 중에 발견되면 늦다.
  3. 인터닝 — 모듈 이름과 위험 타입 문자열을 정수 ID로 바꾸고 역변환표를 만든다. 이후 런타임 경로에서 문자열이 사라진다.
  4. 팩토리 호출 — 각 모듈을 힙에 만들고 Box<dyn Detector>로 받는다. 파라미터를 넘겨 configure한다. 이 시점에 모듈은 필요한 입력 신호를 선언하고, 연결이 비면 기동 실패한다.
  5. 큐 할당 — 그룹마다 고정 용량 SPSC 링버퍼를 하나씩 만든다. 용량은 설정값. 이후로 큐 메모리는 늘지도 줄지도 않는다.
  6. 스레드 기동 — 그룹 스레드 · Arbiter 스레드 · Supervisor 스레드를 띄우고 시계를 주입한다. 실시간 우선순위 지정은 아직 없다 (Phase 1 이후). 지금은 일반 우선순위로 돈다.
이 순서가 주는 것

설정 오류는 전부 기동 전에 드러나고, 할당은 전부 기동 중에 끝난다. 그래서 fast 그룹의 tick 경로에 할당이 0이라는 요구가 성립할 수 있다.

F한 tick 안에서

fast 그룹이 1 kHz로 돈다면 한 주기는 1 ms다. 그 안에서 벌어지는 일은 언제나 같은 순서다.

G무언가 잘못됐을 때

이 프로젝트에서 가장 신경 쓴 부분이다. 감시 시스템의 최악 실패는 오경보가 아니라 조용해지는 것이다. 세 가지 고장이 전부 같은 곳으로 모인다.

HPhase 0 완료 조건 — 달성

완료 조건은 하나였다. 같은 바이너리에 다른 설정을 줘서 서로 다른 감시 구성이 도는 것. 지금 이렇게 돈다.

$ rsm check --config examples/demo-a.yaml

    [fast] 1000.0 Hz  source 1 · detector 1
    [normal] 100.0 Hz  source 1 · detector 1

$ rsm run --config examples/demo-a.yaml --duration-ms 2000
{"ts_ns":...,"level":"CRITICAL","availability":"Available","active":[{"source":"torque_limit","kind":"internal.joint.torque_limit",...}]}
{"ts_ns":...,"level":"NONE","availability":"Available","active":[]}

demo-b.yaml은 모듈 구성이 다르고(이동로봇 · 통신 두절 · 고의 패닉), 같은 바이너리로 돈다. 패닉 메시지가 찍히지만 프로세스는 살아 있고 availability가 Degraded로 바뀐다. 이것이 G2(조합 가능성)의 최소 증명이고, 여기서부터 레퍼런스 모듈을 늘려 v0.5로 간다.
