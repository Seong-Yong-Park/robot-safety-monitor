## 1. 문제 정의

기존 RSM은 **inside-out**이다. 로봇이 발행하는 데이터(관절 토크, 배터리, 통신 상태)를
읽어 위험을 판정한다. 여기에는 구조적 한계가 둘 있다.

**첫째, 로봇이 모르는 것은 RSM도 모른다.** 로봇의 인지가 사람을 놓치면, 그 로봇의
데이터를 보는 감시기도 사람이 없다고 본다. 관측자가 피관측자와 같다.

**둘째, 로봇에 달린 카메라의 사람 감지에는 검증 목록을 닫을 수 없다.**
기능안전 표준(ISO 26262, IEC 61508)이 체계적 고장에 대해 요구하는 것은 요구사항
추적성과 구조적 커버리지인데, 학습된 가중치를 상대로 그것을 만드는 방법이 아직 없다.
로봇이 가는 곳마다 입력 분포가 바뀌므로 검증해야 할 장면의 목록이 끝나지 않는다.

**고정 카메라는 조건이 다르다.** 시야가 고정되고, 조명을 통제할 수 있고, 검증할
장면의 집합이 유한하다. 셋 다 같은 것을 뜻한다 — **인지를 닫힌 문제로 줄일 수 있다.**

Outside-In은 감시자를 로봇 바깥, 작업장에 둔다. 로봇의 자기 보고와 무관하게
독립적으로 관측한다.

> **참고**: NVIDIA Halos for Robotics(2026-06-22 공개)의 Outside-In Safety
> 블루프린트가 같은 구조를 제시한다. 이 문서는 그 **구조를 참조하되 독자 구현**한다
> (D-OI-1).

## 4. 시스템 개념

### 4.1 기존 파이프라인이 그대로 쓰인다

Halos 블루프린트의 구성요소와 RSM 파이프라인이 거의 1:1로 대응한다. **새로 만들
것은 양 끝 둘뿐이다.**

| Halos | RSM | 상태 |
|---|---|---|
| SIPP (센서 입력 처리) | `Source` | **새로 — `rsm-vision`** |
| SAIM (입력 건전성 감시) | `Detector` | 새 모듈 (`comm_timeout`과 같은 계열) |
| PCM (파이프라인 생존 감시) | `Supervisor` | 있음 |
| SEI (이벤트 시간축 융합) | `Arbiter` + TTL | 있음 |
| SDM (명령 번역) | `Sink` | **새로 — `rsm-command`** (권고까지만) |
| SBB (블랙박스) | `JsonlSink` | 있음 |
| Closed-Loop Testing | `VirtualClock` + 리플레이 | 원리 동일 (D-OI-5) |

### 4.2 인지는 별도 프로세스다 (D-OI-4)

```
 ┌───────────────────────┐   인지 결과     ┌──────────────────────────────────────┐
 │  인지 프로세스          │  (위치·거리·    │  RSM                                  │
 │  카메라 → 추론          │   확신도·시각)  │  rsm-vision ─▶ Detector ─▶ Arbiter    │
 │  (현장마다 교체)         │ ─────────────▶ │               ─▶ rsm-command (권고)   │
 └───────────────────────┘                └──────────────────────────────────────┘
        교체 단위                  계약                     공유 프레임워크
```

`rsm-vision`은 **인지 결과를 받는 인터페이스**와 **참조 인지 구현 하나**를 갖는다.
현장에 맞춘 인지는 같은 인터페이스를 말하는 별도 프로세스다.

프로세스를 나누는 이유는 셋이다.

1. **감시자와 감시 대상을 분리한다.** R-OI-04(인지 건전성 감지)는 인지가 별도
   프로세스일 때만 성립한다. 같은 주소공간이면 인지의 고장이 감시기의 고장이 된다.
2. **인지를 바꿔도 프레임워크를 재검증하지 않는다** (G-OI-5). 현장별 튜닝이 잦을수록
   이득이 크다.
3. **코어의 원칙을 지킨다.** GPU·모델 런타임 의존이 코어에 들어오지 않고(D1),
   추론의 가변 지연·할당이 tick 경로에 들어오지 않는다(R-08).

대가는 **프로세스 경계의 지연·유실이 새 위험**이 된다는 것이다. 이것은 기존
`SignalSlot.updated_at` 스테일 판정과 Supervisor로 다룬다 (R-OI-03, R-OI-04).

### 4.3 새 크레이트 둘

| 크레이트 | 역할 | 의존 |
|---|---|---|
| `rsm-vision` | 인지 결과 수신 Source + 인지 건전성 Detector + 참조 인지 구현 | `rsm-core` |
| `rsm-command` | `SafetyState`와 권고 액션을 외부로 내보내는 Sink | `rsm-core` |

**의존 방향은 기존과 같다** — 코어는 둘을 모른다. `rsm-core/Cargo.toml`이 감사 지점이다.

## 5. 흐르는 타입 — 기존 셋을 그대로 쓴다

`Signal` → `HazardEvent` → `SafetyState`. 바뀌는 것은 **내용물뿐**이다.

| 타입 | inside-out | outside-in |
|---|---|---|
| `Signal` | `joint.torque` (Scalar) | `zone.min_distance` (Distance), `zone.person_count` (Scalar) |
| `HazardEvent.category` | `Internal` | **`External` 또는 `Ml`** |
| `HazardEvent.confidence` | 항상 1.0 | **인지 출력 (< 1.0)** |
| `SafetyState` | level + availability | **+ `recommended_action`** (R-18) |

`confidence`가 처음으로 1.0이 아니게 된다. `HazardEvent::with_confidence()`가 그때
첫 호출자를 갖는다. Arbiter가 이 값을 판정에 쓸지는 PRD R-13(P1) 사안이다.

위험 타입 이름은 PRD D20을 따른다. 예: `external.zone_a.min_distance`,
`ml.zone_a.person_intrusion`. **같은 구역을 보는 카메라 둘은 같은 이름**을 써서
Arbiter가 합치게 한다.

## 6. 요구사항

### 6.1 Must-Have (P0)

| ID | 요구사항 | 인수 기준 (요약) |
|---|---|---|
| R-OI-01 | **독립 관측** — 로봇이 발행하는 어떤 신호도 입력으로 요구하지 않고 판정이 성립한다 | 로봇 통신을 끊어도 `level`이 정상 산출된다 |
| R-OI-02 | **구역(zone) 모델** — 감시 구역과 그 안의 판정 규칙을 YAML로 선언한다 | 구역 정의 오류·중복은 기동 실패 (PRD R-02 계승) |
| R-OI-03 | **인지 결과 인터페이스** — 별도 프로세스의 인지 결과를 `Signal`로 변환한다 | 메시지에 형식 버전과 관측 시각이 있다. 지연·유실은 스테일로 판정 (`SignalSlot.updated_at` 재사용) |
| R-OI-04 | **인지 건전성 감지** — 인지 프로세스의 끊김·과지연, 카메라의 가림(occlusion)·분포 밖 입력을 위험으로 낸다 | SAIM·PCM 상당. 인지가 멈추면 `availability`가 `Degraded` 이상 |
| R-OI-05 | **명령 미발행** — 액추에이터를 구동하는 인터페이스를 제공하지 않는다 | 출력은 `SafetyState`와 권고(R-18)뿐. 문서에 명시 (D-OI-2) |
| R-OI-06 | **다중 카메라 융합** — 카메라 N대의 관측을 하나의 `SafetyState`로 합친다 | 같은 구역을 보는 관측은 같은 위험 타입 이름 (D20) |
| R-OI-07 | **감시 대상 다수** — 한 작업장에서 로봇 N대를 동시에 다룬다 | 로봇별 구역·권고를 구분해 출력 |
| R-OI-08 | **지연 예산** — 관측에서 권고까지의 지연을 계측해 출력한다 | 30 fps 입력 기준. PRD `GroupStats` 확장 |
| R-OI-09 | **기록·감사 추적** — 판정 근거를 재구성 가능한 형태로 남긴다 | SBB 상당. JSONL + 인지 결과 참조 (PRD D15) |

**권고 액션**은 코어의 `SafetyState`를 바꾸므로 이 문서가 아니라 **PRD R-18**(D21로
P0 승격)이 담당한다.

### D-OI-5의 재검토 조건

**사람이 로봇에 실제로 접근하는 위험 장면을 안전하게 녹화할 수 없을 때** 시뮬레이터를
재검토한다. 그때의 후보는 Isaac Sim(D13에 "후속 재검토"로 이미 언급)이다.

## 8. 인증 포지셔닝 — 명시적으로 열어 둔다

§1의 논리("고정 카메라는 인지를 닫힌 문제로 줄인다")는 인증 가능성을 함의한다.
그런데 D6(비인증 자문 계층)과 D-OI-2(권고만)는 그 길을 택하지 않는다.

이것은 모순이 아니라 **순서**다. 인증은 제품이 아니라 개발 프로세스에 매기는 것이고,
그 프로세스(요구사항 추적성, 구조적 커버리지, 독립 검증)는 별도의 투자다.
다만 **설계에서 그 길을 막지 않는다** — R-OI-14가 그 조항이며, D-OI-4의 프로세스
분리가 "인지(검증 어려움)와 판정(결정적)"의 경계를 물리적으로 만든다.

권고 필드의 사용자가 그 출력으로 실제 정지를 걸기 시작하면 사실상 안전 기능이
된다. 그 경우의 책임 경계는 이 소프트웨어가 아니라 통합자의 안전 회로에 있다
(PRD D6).

| Q-OI-5 | **인지 지연 상한** — 몇 ms부터 `Degraded`인가 | Phase 1 | 30 fps면 한 프레임 33 ms. 스테일 임계를 설정으로 받는다 |
