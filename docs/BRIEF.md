# Robot Safety Monitor — 한 장 요약

새 대화를 시작할 때 이 문서만 읽어도 문맥이 서도록 쓴 압축본이다.
근거와 상세는 [PRD.md](PRD.md)와 [TECH_STACK.md](TECH_STACK.md)에 있다.

## 무엇을 만드나

로봇의 위험을 감지하는 SW 모듈을 표준 트레이트로 규격화하고, **YAML 설정 파일만으로
조합**하는 Rust 프레임워크.

지금 대부분의 로봇 스택에서 "관절 토크가 한계를 넘었다", "사람이 너무 가깝다" 같은
감지 로직은 각 노드나 제어기 안에 흩어져 하드코딩되어 있다. 그래서 플랫폼이 바뀌면
다시 짜야 하고, 무엇을 어떤 조건으로 감시하는지 한눈에 볼 수 없고, 검증도 어렵다.

## 구조

```
 Source ──▶ Detector ──▶ Arbiter ──▶ Sink
 (입력)     (감지 단위)   (융합·판단)  (출력)
   ▲           ▲            ▲          ▲
   └──── YAML 설정이 네 단계를 전부 선언 ────┘
        + Supervisor : 모듈 생존·입력 스테일 감시
        + Clock      : 시계를 외부에서 주입
```

흐르는 타입은 셋뿐이다. `Signal`(Source→Detector), `HazardEvent`(Detector→Arbiter),
`SafetyState`(Arbiter→Sink). 배관이 고정돼 있어 모듈을 추가해도 코어가 바뀌지 않는다.

## 증명하려는 주장 셋

| | 주장 | 판정 기준 |
|---|---|---|
| G1 | 설정만 바꾸면 다른 감시 구성이 돈다 | 같은 바이너리 + 다른 YAML로 3종 구성 구동 |
| G2 | 새 모듈 추가가 코어 수정 0줄이다 | 신규 모듈 1개에 `rsm-core` 변경 없음 |
| R-06 | 침묵을 안전으로 오해하지 않는다 | 감시 불가 시 `MonitorUnavailable` 명시 발행 |

세 번째가 이 프로젝트의 성격을 결정한다. 감시 시스템의 최악 실패는 오경보가 아니라
조용해지는 것이다. 그래서 TTL(이벤트가 스스로 소멸)과 Supervisor(감시기 자체의 생존)를
독립된 두 메커니즘으로 분리했다.

## 하는 것 / 안 하는 것

| 한다 | 안 한다 |
|---|---|
| 내부 위험 감지 — 관절 한계·토크·온도·배터리·통신 끊김 | **정지·감속 명령 발행** — 대응은 로봇 제어기 책임 |
| 외부 위험 감지 — 사람 근접·장애물 거리·속도-거리 규칙 | 인증(safety-rated) 등급 — v1은 비인증 자문 계층 |
| 일관된 스키마의 위험 이벤트 발행과 알림 | ML 모델 자체 개발 — 공개 사전학습 모델 래핑만 |
| 리플레이 기반 재현 가능한 검증 | 동적 플러그인(.so) 로드 — P2로 |

## 크레이트

| 크레이트 | 역할 | 상태 |
|---|---|---|
| `rsm-core` | 트레이트·타입·레지스트리·설정·스케줄러·Supervisor. **미들웨어 비의존** | `time.rs`만 구현 |
| `rsm-modules` | 레퍼런스 감지 모듈 | 뼈대만 |
| `rsm-cli` | 실행 파일 | 미생성 |
| `rsm-ml` | ONNX 모델 래퍼 Detector | Phase 2 |
| `rsm-mcap` | rosbag2/MCAP 리플레이 Source | Phase 3 (선택) |
| `rsm-ros2` | rclrs 기반 어댑터 | Phase 3 |

의존 방향이 곧 설계 원칙이다. `rsm-core`의 `Cargo.toml`에 ROS가 없으므로 코어 코드
어디서도 ROS를 부를 수 없다. 규율이 아니라 빌드 구조로 강제된다.
