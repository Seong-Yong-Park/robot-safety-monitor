## 1. 문제 정의

로봇의 위험은 두 방향에서 온다. **내부**(모터 과열, 관절 토크 한계 초과, 배터리 저전압, 통신 타임아웃, 상태 추정 발산 등)와 **외부**(사람 근접, 장애물, 낙상 위험 지형, 작업공간 침입, 조도/센서 열화 등)이다. 현재 대부분의 로봇 스택에서 이 감지 로직은 각 애플리케이션 노드나 제어기 안에 흩어져 하드코딩되어 있어, 플랫폼이나 운용 상황이 바뀔 때마다 감지 로직을 다시 짜야 하고, "어떤 위험을 어떤 조건에서 감시하고 있는가"를 한눈에 확인하거나 검증하기 어렵다.

RSM은 **위험 감지 모듈을 표준 인터페이스로 규격화**하고, **설정 파일로 조합**하여 상황에 맞는 감시 구성을 만들 수 있게 하는 SW 프레임워크다. 감지 결과를 일관된 위험 이벤트로 발행하되, 실제 정지·감속 같은 대응 동작은 로봇 측(제어기·실행 계층)에 맡긴다.

해결하지 않을 경우의 비용: 플랫폼별 중복 구현, 감시 범위의 불투명성, 검증 부담 증가, 새로운 센서/위험 유형 추가 시 기존 코드 전면 수정.

## 2. 목표

| # | 목표 | 성공 판단 기준 |
|---|---|---|
| G1 | **조합 가능성** — 코드 수정 없이 설정만으로 감시 구성을 바꿀 수 있다 | 3개 이상의 서로 다른 시나리오 구성(§8.1)을 동일 바이너리 + 다른 설정 파일로 구동 |
| G2 | **확장성** — 새 감지 모듈 추가가 격리된 작업이다 | 신규 모듈 1개 추가 시 `rsm-core` 코드 변경 0줄, 템플릿 기반으로 반나절 내 작성·등록 가능 |
| G3 | **일관된 위험 표현** — 모든 모듈이 같은 스키마의 위험 이벤트를 낸다 | 이벤트 스키마 1종으로 내부/외부/ML 모듈 전부 표현, 소비자는 모듈 종류를 몰라도 처리 가능 |
| G4 | **결정적·저지연 동작** — 감시 루프의 실행 시간이 예측 가능하다 | 주기 그룹별 tick 지터 상한을 측정·문서화; 동적 메모리 할당은 초기화 단계에만. **caveat: 이는 통계적 관측(P99)이지 WCET 증명이 아니다** — 타겟 CPU가 out-of-order·투기 실행·캐시를 쓰는 한 전통적 WCET 보장은 불가하며, 이것이 v1을 비인증 자문 계층(D6)으로 두는 근거 중 하나다. 또한 Windows에서 측정한 수치는 참고용이고 공식 수치는 Linux(`SCHED_FIFO`)에서 재측정한다 |
| G5 | **검증 가능성** — 모듈 단위·조합 단위로 재현 가능한 테스트가 있다 | 각 모듈에 기록 데이터 리플레이 기반 단위 테스트; 조합 구성에 대한 통합 테스트; 리플레이 결과는 실행 속도와 무관하게 동일 |

## 4. 사용자 및 사용자 스토리

### 페르소나

- **로봇 통합 개발자(Integrator)** — 특정 로봇에 RSM을 붙이고 상황에 맞는 감시 구성을 만드는 사람. v1의 1차 사용자이며 곧 나 자신.
- **모듈 개발자(Module Author)** — 새로운 감지 모듈을 작성하는 사람.
- **소비 시스템(Consumer)** — 위험 이벤트를 받아 실제 대응을 수행하는 제어기/실행 계층/운영자 알림 시스템.

### 스토리 (우선순위 순)

1. As an **Integrator**, 나는 설정 파일에 사용할 모듈과 파라미터를 나열하는 것만으로 감시 파이프라인을 구성하고 싶다. 그래야 플랫폼/상황이 바뀔 때 코드를 다시 빌드하지 않아도 된다.
2. As a **Consumer**, 나는 위험의 종류·심각도·출처·근거를 담은 단일 스키마의 이벤트를 받고 싶다. 그래야 모듈 종류와 무관하게 대응 로직을 작성할 수 있다.
3. As a **Module Author**, 나는 정해진 트레이트(초기화 / 입력 선언 / 주기 평가 / 건강 상태)만 구현하면 모듈이 등록되기를 원한다. 그래야 프레임워크 내부를 몰라도 모듈을 추가할 수 있다.
4. As an **Integrator**, 나는 여러 모듈이 동시에 위험을 보고할 때 하나의 종합 위험 수준으로 합쳐진 결과를 받고 싶다. 그래야 소비자가 중복·상충 이벤트를 직접 처리하지 않아도 된다.
5. As an **Integrator**, 나는 모듈이 필요로 하는 입력이 없거나 끊겼을 때 이를 "감시 불가" 상태로 명시적으로 알고 싶다. 그래야 침묵을 "안전함"으로 오해하지 않는다. *(엣지 케이스 — 핵심)*
6. As an **Integrator**, 나는 기록된 데이터를 리플레이하여 특정 구성이 기대한 시점에 이벤트를 내는지 확인하고 싶다. 그래야 실기 없이 회귀 테스트가 가능하다.
7. As a **Module Author**, 나는 모듈이 패닉하거나 주기를 초과했을 때 파이프라인 전체가 멈추지 않고 해당 모듈만 "고장" 상태로 격리되기를 원한다. *(엣지 케이스)*
8. As a **Module Author**, 나는 추론 시간이 수십 ms로 튀는 ML 감지기를 작성해도 1 kHz로 도는 다른 모듈에 영향을 주지 않기를 원한다. *(v1 신규 — 주기 그룹)*
9. As an **Integrator**, 나는 런타임에 특정 모듈을 활성/비활성 전환하고 싶다 (예: 작업 모드 전환). *(P1)*

## 5. 시스템 개념 (아키텍처)

### 5.1 파이프라인

```
 ┌──────────────┐   ┌──────────────────────────────┐   ┌────────────┐   ┌──────────────┐
 │  Sources     │   │  Detectors (감지 모듈)        │   │ Arbiter    │   │  Sinks       │
 │ (입력 어댑터) │──▶│  internal.* / external.* /   │──▶│ (융합·판단) │──▶│ (알림/출력)   │
 │ 센서·상태·   │   │  ml.*  각 모듈 = 독립 평가 단위│   │ 종합 위험   │   │ 로그·토픽·   │
 │ 진단 신호     │   │  → HazardEvent 발행           │   │ 수준 산출   │   │ stdout       │
 └──────────────┘   └──────────────────────────────┘   └────────────┘   └──────────────┘
         ▲                        ▲                          ▲                 ▲
         └────────── 설정 파일(YAML)이 4단계 모두의 구성·파라미터·연결을 선언 ──────────┘
                              + Supervisor: 모듈 생존/주기/입력 유효성 감시
                              + Clock: 외부 주입 (실기: 단조 시계 / 리플레이: 가상 시계)
```

- **Source**: 외부 데이터를 프레임워크 내부 표준 신호(`Signal<T>`)로 변환하는 어댑터. 미들웨어 의존성은 여기(와 Sink)에만 존재한다.
- **Detector**: 하나의 위험 유형을 평가하는 최소 단위. `internal.*`(자체 상태), `external.*`(환경), `ml.*`(학습 모델 래퍼) 네임스페이스. 입력 신호 선언 → 주기 평가 → `HazardEvent` 발행.
- **Arbiter**: 다수의 `HazardEvent`를 하나의 `SafetyState`로 융합. 정책 교체 가능.
- **Sink**: `HazardEvent`/`SafetyState`/Supervisor 건강 상태를 외부로 내보내는 출력 어댑터.
- **Supervisor**: 모듈 자체의 건강(주기 초과, 입력 스테일, 패닉)을 감시하고 `MonitorUnavailable`을 낸다. TTL 만료(이벤트 소멸)와는 **독립된 메커니즘** — 감시기가 죽었을 때 위험 이벤트가 조용히 사라지는 침묵 실패를 막는다.
- **Clock**: 코어는 시계를 직접 호출하지 않고 `Clock` 트레이트 구현체를 주입받는다.

### 5.2 실행 모델 — 주기 그룹 (확정)

| 그룹 | 예시 주기 | 대상 모듈 | 실행 방식 |
|---|---|---|---|
| `fast` | 1 kHz | 관절 한계·토크·통신 타임아웃 | 전용 스레드, 단일 tick 내 순차 실행, 실행 순서 결정적 |
| `normal` | 100 Hz | 배터리·온도·근접 거리·속도-거리 규칙 | 전용 스레드, 동일 |
| `async` | 입력 주도 | ML 래퍼(비전 추론) 등 가변 지연 모듈 | 별도 스레드, 결과를 이벤트로만 전달 |

그룹 간 이벤트 전달은 lock-free SPSC/MPSC 큐(고정 용량, 초기화 시 할당). 그룹 수와 주기는 설정 파일에서 선언. 모듈은 자신이 속할 그룹을 설정에서 지정받는다. 한 그룹의 지연이 다른 그룹을 막지 않는다.

### 5.3 코드 구조 — Rust 워크스페이스 (확정)

| 크레이트 | 역할 | 의존성 방향 |
|---|---|---|
| `rsm-core` | 트레이트(`Source/Detector/Arbiter/Sink/Clock`), `HazardEvent`/`SafetyState` 타입, 레지스트리, 설정 로더, 스케줄러(주기 그룹), Supervisor | 외부 미들웨어 의존 없음. `std` 사용하되 `alloc` 경계 의식 (R-22) |
| `rsm-modules` | 레퍼런스 Detector/Arbiter 구현(R-09), 파일 리플레이 Source, JSONL/stdout Sink | `rsm-core` |
| `rsm-ml` | 사전학습 모델 래퍼 Detector + 추론 런타임 바인딩 | `rsm-core` (feature flag로 선택 빌드) |
| `rsm-ros2` | rclrs 기반 Source/Sink 어댑터, `rsm_msgs` 정의, 노드 실행 파일, ROS 시계 → `Clock` 구현 | `rsm-core`, `rsm-modules`, rclrs |
| `rsm-tools` (Python) | 설정 검증, 리플레이 실행·비교, 결과 리포트 | CLI 경유 |

모듈 간 계약은 **Rust 트레이트 API(semver)** 이며 v1에는 바이너리 ABI 경계가 없다. rclrs로 어댑터를 쓰는 한 FFI가 발생하지 않는다.

## 6. 요구사항

### 6.1 Must-Have (P0)

| ID | 요구사항 | 인수 기준 (요약) |
|---|---|---|
| R-01 | **모듈 트레이트 규격**: `Source / Detector / Arbiter / Sink / Clock` 5종의 트레이트를 정의한다 | `configure(&Params)`, `declare_inputs()/outputs()`, `tick(now: Instant)`, `health()` 상당의 계약; rustdoc 문서화 |
| R-02 | **선언적 조합**: YAML로 주기 그룹·모듈·파라미터·신호 연결을 선언하면 파이프라인이 생성된다 | 스키마 검증; 미등록 모듈·미연결 입력·타입 불일치·미지정 그룹은 **기동 실패**로 보고 (묵시적 무시 금지) |
| R-03 | **모듈 레지스트리**: 모듈은 이름으로 등록되고 설정에서 이름으로 참조된다 | 등록 = `(name, factory_fn)` 쌍. 신규 모듈 등록 시 `rsm-core` 수정 없음. 팩토리 시그니처는 P2 동적 로드와 호환 |
| R-04 | **HazardEvent 스키마 단일화** | 필수 필드: `id`, `source_module`, `category`(internal/external/ml), `type`, `severity`(순서형: NONE/ADVISORY/WARNING/CRITICAL), `confidence`, `timestamp`, `evidence`, `ttl`. `evidence`는 평탄한 `(key, scalar)` 목록 — 향후 `#[repr(C)]` 미러 가능해야 함 |
| R-05 | **Arbiter 기본 정책**: max-severity + TTL | 동일 `type`은 최신값으로 갱신; `ttl` 만료 시 비활성; 정책 트레이트로 교체 가능. TTL 기본값 = 모듈 주기의 2–3배 |
| R-06 | **감시 불가 상태 명시**: 입력 스테일/모듈 패닉/주기 초과 시 `MonitorUnavailable` 발행 | Supervisor는 Detector 그룹과 독립 스레드; 침묵 상태가 NONE으로 해석되지 않음; `SafetyState`에 `monitor_availability` 필드 포함 |
| R-07 | **모듈 고장 격리**: 한 모듈의 패닉/타임아웃이 다른 모듈과 파이프라인을 중단시키지 않는다 | `catch_unwind` 경계; 고장 모듈은 `FAULTED` 전이, 재시작 정책(설정) 적용; 다른 그룹·같은 그룹의 나머지 모듈 정상 동작 테스트 |
| R-08 | **결정적 실행**: 주기 그룹 스케줄링, 초기화 이후 힙 할당 최소화 | 그룹별 tick 실행 시간·초과 횟수 계측 내장; `fast` 그룹 tick 경로에서 할당 0 (테스트로 검증) |
| R-09 | **레퍼런스 모듈 세트** | internal: 관절 한계(위치/속도/토크), 배터리 저전압, 온도 임계, 통신 타임아웃 / external: 최소 거리(근접) 위반, 속도-거리 규칙 / **ml: 공개 사전학습 사람 검출 모델 래퍼 → 근접 위험** (모델 자체는 개발하지 않음) / Source: 파일 리플레이 1종 / Sink: JSON Lines, stdout |
| R-10 | **시계 주입 + 리플레이 테스트** | 코어 내 `now()` 직접 호출 0건(lint/grep으로 검증); 가상 시계로 리플레이 시 결과가 실행 속도와 무관하게 동일; 레퍼런스 모듈 전부 리플레이 테스트 보유 |

| D16 | **타겟: x86_64 Linux/Windows(개발) + aarch64 Linux(ARM SBC).** **Windows는 개발·CI 전용이며 주기 성능 요구(G4/R-03)의 판정 대상이 아니다.** CI에 aarch64 빌드·테스트를 처음부터 포함(단 `rsm-ml` 제외), **실기 검증은 Phase 2에 1회** | 보유 ARM 보드 있음. `no_std` 베어메탈 MCU는 v1 대상이 **아님**(주기 그룹=OS 스레드, `catch_unwind`=되감기, `Box<dyn>`=힙 전제가 무너짐) — 그쪽은 R-21/R-22 영역. 공개 저장소면 GitHub Actions arm64 러너를 쓸 수 있어 크로스 빌드 부담이 줄어듦. **Windows 단서(Phase 0 실측)**: Windows의 `thread::sleep` 분해능이 굵어 매 tick 약 1~1.6 ms가 밀린다(1 kHz 설정이 실측 533 Hz, 100 Hz 설정이 86 Hz). 같은 코드가 Linux에서는 초과분 0.09 ms. 타이머 분해능을 올리려면 `timeBeginPeriod(1)` 등 `unsafe`가 필요하므로 코어에 들이지 않는다 — Windows에서 개발할 때는 `fast` 그룹 주기를 낮춰 쓴다 |

| D18 | **코딩 규칙 확정** — `rsm-core`에 `forbid(unsafe_code)`, `clippy::pedantic` 켬, `unwrap/expect/panic` deny(라이브러리), `indexing_slicing`은 핫패스 한정, `cargo-deny`로 라이선스·금지·취약점 검사 | 상세는 TECH_STACK T10. 첫 커밋부터 CI 적용 |
| D19 | **투입 시간: 주당 10시간** | §8 공수·기간의 기준 |
| D20 | **위험 타입 이름 규약: `<category>.<subject>.<condition>`** (예: `internal.joint.torque_limit`, `internal.battery.low`, `external.obstacle.min_distance`). (1) 첫 토막은 `Category`(`internal`/`external`/`ml`)와 일치한다. (2) `condition`은 값이 아니라 **위반**을 말한다 (`torque`가 아니라 `torque_limit`). (3) **이름이 같으면 Arbiter가 같은 위험으로 합친다** — 소비자가 따로 봐야 할 위험은 이름을 나누고(`internal.arm_l.torque_limit` / `internal.arm_r.torque_limit`), 같은 조건의 중복 관측자만 이름을 공유한다. 모듈 `name`은 **인스턴스("어디서", `front_lidar`)** 이며 위험 이름과 독립이다 | 설정·로그·ROS 토픽에서 같은 문자열을 쓰고(R-04), Arbiter 병합 키가 이 이름이므로(D4) "이름 = 병합 단위"를 규약으로 못 박아야 설정 실수가 조용한 덮어쓰기로 이어지지 않는다. 런타임에는 인터닝된 `HazardTypeId`라 이름 길이가 비용이 아니다. 접두어-Category 일치는 v0.5까지 관례로 두고 Phase 1에 `configure` 단계 기동 실패로 강제한다(D20-a) |

## 11. 용어

| 용어 | 정의 |
|---|---|
| HazardEvent | 하나의 Detector가 발행하는 단일 위험 관측. TTL 동안 유효한 "주장" |
| SafetyState | Arbiter가 산출하는 종합 상태 (최고 심각도 + 활성 위험 목록 + 감시 가용성) |
| MonitorUnavailable | 감시 기능 자체가 유효하지 않음을 알리는 이벤트 (입력 스테일·모듈 고장) |
| TTL | Time-To-Live. 이벤트 유효 시간. 갱신 없이 만료되면 비활성 |
| 주기 그룹 | 같은 주기로 같은 스레드에서 순차 실행되는 모듈 집합 |
| Clock | 코어가 주입받는 시간 소스 트레이트 (단조/가상) |
| ABI | 컴파일된 바이너리 간 호출 규약·레이아웃 약속. v1에는 경계 없음, P2(R-19)에서 C ABI로 관리 |
| Source / Detector / Arbiter / Sink / Supervisor | §5.1 참조 |
